# 個別支援計画「AI下書き」手順書（ボットの定期処理用）

目的：職員が計画画面の「AIで下書きを依頼」を押したら、ボット自身のAIが業務日誌・日報・自動集計を読んで、計画の各項目の**下書き**を入れる。
**外部のAIサービスには送らない。** 文章を書くのは、この定期処理を実行しているボット（エージェント）自身。職員が必ず確認・修正して確定する。

このリポジトリは公開されるため、利用者の個人情報・実際の下書き・キーはここに書かない。

## 流れ
1. 画面（管理者のみ）→ `bp_plan_draft_requests` に1行（status=pending）
2. 定期処理が `collect` → 依頼ごとの材料JSONができる（個人情報を含む。0600、/tmp/ai-draft/）
3. ボットが材料を読んで、下書きJSONを作る（下記の指針）
4. `apply` → 計画の各項目に書き込み、版履歴に「AI下書きを反映」を追加、依頼を done にして、材料と下書きのファイルを削除
5. 画面に「下書き済み（日時）」と、項目ごとに「AI下書き・要確認」が出る。職員が直すか「確認した」にチェックするまで、本案の確定には進めない

## コマンド
```
node tools/draft-plans.js collect [--office RYDEEN] [--out /tmp/ai-draft/collect.json]
node tools/draft-plans.js apply --draft /tmp/ai-draft/draft.json [--collect /tmp/ai-draft/collect.json]
node tools/draft-plans.js fail <request_id> "理由"     # 下書きを作れないとき（画面にエラー表示）
node tools/draft-plans.js clean                         # 作業ファイルを全削除
```
service_role キーは環境変数 `SUPABASE_SERVICE_ROLE_KEY`（または `SUPABASE_SERVICE_KEY`）か `/workspace/b-portal/.env.local`。キーは画面にもログにも出さない。
`pending` が 0 件なら何もせず終了してよい（下書きJSONも作らない）。

## collect の出力
`requests[]` ごとに：`request_id` / `plan_id` / `worker_name`（氏名のみ。住所・生年月日・受給者証番号などは含めない）/ `period`（計画期間）/ `stage` / `already_filled_fields`（職員が入力済みの項目）/ `previous_plan`（前版の計画。あれば）/ `auto_summary`（利用日数・欠席・利用率・平均作業時間・体調・主な作業などの自動集計）/ `journal`（直近約90日の業務日誌）/ `daily_reports`（利用者の日報）。
トップの `sections` は書く対象（`assessment` / `monitoring` / `plan` とその項目名）。会議録（meeting）は事実を知り得ないので対象外。

## 下書きJSON
```json
{ "drafts": [ { "request_id": "...", "plan_id": "...",
  "sections": { "assessment": { "利用者概要": "…", "本人の意向": "…" },
                "monitoring": { "前期の目標と評価": "…" },
                "plan":       { "長期目標": "…" } } } ] }
```
項目名は collect の `sections[].fields` と**完全一致**で書く。書かない項目は空欄のまま（空欄は印刷時に【要確認】になる）。1項目あたり2000字まで。
`apply` は、職員がすでに書いた項目は上書きしない。前回のAI下書き（まだ要確認の項目）は新しい下書きで置き換わる。確定・署名後の計画は書き込まず error にする。

## 下書きを作る際の指針
- **観察事実に基づく。** 日誌・日報・集計に出ていることだけを根拠にする。数字（利用日数、利用率、作業時間など）は collect の値をそのまま使う。
- **記録にないことは書かない。** 本人・家族の意向、病名や診断、生活状況、強み・課題の原因などを推測で作らない。材料がない項目は空欄にするか、「〜の記録がありません。【要確認】」とだけ書く。
- **断定しない。** 「〜の様子が見られました」「〜と考えられます」の形にし、職員が本人・家族に確認すべき点には【要確認】を残す。目標・支援内容は「案」として書き、本人の希望を確認する旨を添える。
- **です・ます調。** 利用者本人が読んでも分かる、短くて平易な文にする。専門用語・差別的な表現・本人を評価で決めつける言い方は避ける。
- **国の様式にとらわれない。** 項目名の趣旨に合わせて、実際に職員が使いやすい書き方にする。
- **送迎・食事（食事提供）は書かない。** この事業所は行っていない。
- 体調の波や欠席が多いときは、責める書き方をせず、背景の確認（【要確認】）と通所日数・時間の調整案として書く。
- 氏名は本文に必須ではない。使う場合は「○○さん」。他の利用者の情報を混ぜない。
- 書いたあと、(1) 記録にない事実を書いていないか (2) 数字が collect と合っているか (3) 送迎・食事に触れていないか、を見直す。

## 定期実行（routine）の設定案
- 頻度：営業日の日中に15〜30分おき（例：平日 8:30〜18:00）。夜間・早朝は実行しない（通知もしない）。依頼があるときだけ動くので、`collect` の `pending` が 0 なら即終了する。
- 手順：`collect` → pending が 0 ならファイルを `clean` して終了 → あれば材料を読んで下書きJSONを作る → `apply` → 失敗した依頼だけ `fail` で理由を記録（画面に出る）→ `clean`。
- 必要な権限・環境：box 上の Node 20 以上、`/workspace/portal-b-work`、service_role キー（上記）。外部送信は不要。メッセージ・通知は出さない。
- ファイルは /tmp/ai-draft/ に 0600 で作り、`apply` 成功後に自動削除。失敗時は残るので、確認後に `clean` する。
- ボットが同時に動かないよう、1回の実行が終わってから次を始める。同時に職員が編集していたときは `apply` が書き込まずに pending のまま残し、次回に再処理する。
